# Лекция 6. Traits — общий контракт для разных типов

> Трейт — это «список умений», который разные типы могут реализовать. Если в Java это интерфейс, а в
> Go — interface, то в Rust это трейт. Трейты — главный инструмент абстракции в Rust: на них держатся
> `Serialize`/`Deserialize`, `From`, `sqlx::FromRow`, обработка ошибок и тестируемость. Эта лекция
> объясняет, как объявлять и реализовывать трейты, как использовать их как параметры функций, что такое
> `From`/`Into`, и как это связано с `Box<dyn>` из лекции 5. В конце — разбор задач блока 6.

---

## 1. Зачем нужны трейты

Представь две разные структуры: фигурка и заказ. Обе можно «коротко описать одной строкой». Без трейтов
ты напишешь две отдельные функции `figurine_short(...)` и `order_short(...)`, и любая общая логика
(«напечатать описание чего угодно») их не свяжет.

Трейт говорит: «есть умение `short()`; кто его реализует — тот умеет коротко описываться». После этого
можно писать код, который работает с **любым** типом, обладающим этим умением. Это и есть абстракция:
писать логику против **контракта**, а не против конкретного типа.

---

## 2. Объявление и реализация трейта

```rust
// 1. Объявляем контракт
trait Summary {
    fn short(&self) -> String;   // умение: вернуть короткое описание
}

// 2. Реализуем для конкретных типов
struct Figurine { name: String, status: String }
struct Order    { requester_name: String, mode: String }

impl Summary for Figurine {
    fn short(&self) -> String {
        format!("Фигурка «{}» ({})", self.name, self.status)
    }
}

impl Summary for Order {
    fn short(&self) -> String {
        format!("Заказ от {} [{}]", self.requester_name, self.mode)
    }
}
```

Теперь у обоих типов есть метод `.short()`:
```rust
let f = Figurine { name: "Ворон".into(), status: "available".into() };
let o = Order { requester_name: "Аня".into(), mode: "request".into() };
println!("{}", f.short());
println!("{}", o.short());
```

`&self` означает «метод берёт ссылку на объект, читает его, не забирая владение» (см. лекции 2–3).

---

## 3. Методы по умолчанию

Трейт может дать **готовую** реализацию метода, которую типы могут не переопределять:
```rust
trait Summary {
    fn short(&self) -> String;

    // метод по умолчанию — использует short()
    fn announce(&self) -> String {
        format!(">>> {}", self.short())
    }
}
```
Тип обязан реализовать только `short()`; `announce()` он получит бесплатно. Это снижает дублирование —
типичный приём в стандартной библиотеке (например, у итераторов сотни методов по умолчанию).

---

## 4. Трейт как параметр функции — `impl Trait`

Главная польза: одна функция работает с любым типом, реализующим трейт.
```rust
fn print_summary(item: &impl Summary) {
    println!("{}", item.short());
}

print_summary(&f);   // работает с Figurine
print_summary(&o);   // и с Order
```
`&impl Summary` читается как «ссылка на что угодно, что реализует `Summary`». Не надо писать функцию
под каждый тип — пишешь одну под контракт.

Это то же самое, что дженерик с ограничением (две записи эквивалентны):
```rust
fn print_summary<T: Summary>(item: &T) {   // <T: Summary> — "T, ограниченный трейтом Summary"
    println!("{}", item.short());
}
```
`T: Summary` называется **trait bound** — «ограничение трейтом»: T может быть любым типом, **лишь бы** он
реализовывал `Summary`.

---

## 5. Статическая vs динамическая диспетчеризация (связь с лекцией 5)

Есть два способа «принять любой тип с трейтом»:

```rust
// СТАТИЧЕСКАЯ: компилятор делает отдельную копию функции под каждый конкретный тип (мономорфизация)
fn a(item: &impl Summary) { ... }      // быстро, но код раздувается

// ДИНАМИЧЕСКАЯ: один код, тип выбирается в рантайме через vtable
fn b(item: &dyn Summary) { ... }       // гибко, чуть медленнее
```

- `&impl Summary` / `<T: Summary>` → **статика**: быстрее, но под каждый тип своя копия машинного кода.
- `&dyn Summary` / `Box<dyn Summary>` → **динамика**: один код, разные типы в одной коллекции (см. л.5).

Правило: если хочешь хранить **разные** типы вместе (`Vec<Box<dyn Summary>>`) — нужна динамика. Если просто
пишешь обобщённую функцию — бери статику (`impl Trait`), она быстрее.

---

## 6. `derive` — трейты «на халяву»

Многие трейты компилятор реализует за тебя через `#[derive(...)]`. Ты это уже видел в моделях Gotiga:
```rust
#[derive(Debug, Clone, Serialize, Deserialize, sqlx::FromRow)]
pub struct Note { ... }
```
- `Debug` → можно печатать через `{:?}`.
- `Clone` → появляется метод `.clone()`.
- `Serialize`/`Deserialize` (из serde) → структура умеет превращаться в JSON и обратно.
- `sqlx::FromRow` → структура умеет собираться из строки БД.

Это всё трейты. `derive` — просто способ не писать их реализацию руками. Открой `models/mod.rs` — там
`derive` почти на каждой структуре.

---

## 7. Трейт `From` и `Into` — стандартная конверсия

`From` — встроенный трейт «как получить один тип из другого». Реальный пример в Gotiga
(`models/mod.rs:1224`):
```rust
impl From<&User> for UserDto {
    fn from(user: &User) -> Self {
        UserDto {
            id: user.id,
            name: user.name.clone(),
            // ВНИМАНИЕ: пароль, ip и т.п. сюда НЕ кладём — DTO это безопасная "витрина"
        }
    }
}
```
Зачем? Модель `User` содержит секреты (хеш пароля, IP). Наружу клиенту отдаём **DTO** (Data Transfer
Object) — урезанную версию без секретов. `From` — стандартный способ описать это превращение.

**Бонус:** как только ты реализовал `From<A> for B`, автоматически появляется `Into` в другую сторону —
можно писать `.into()`:
```rust
let dto: UserDto = (&user).into();   // работает само, потому что есть From<&User> for UserDto
```
Не реализуй `Into` руками — реализуй `From`, а `.into()` получишь бесплатно.

## 8. Где трейты уже работают на тебя в Gotiga

- `AppError` реализует трейт `IntoResponse` (`error.rs:31`) → поэтому ошибку можно вернуть из хендлера, и axum сам превратит её в HTTP-ответ.
- `AppError` реализует `From<sqlx::Error>` (через `#[from]`, `error.rs:12`) → поэтому оператор `?` сам конвертирует ошибку БД в `AppError`.
- `#[derive(Serialize)]` (трейт из serde) → поэтому `Json(note)` умеет отдать структуру как JSON.
- `sqlx::FromRow` → поэтому `query_as::<_, Note>` собирает `Note` из строки.

То есть половина «магии» бэкенда — это просто чужие трейты, которые твои типы реализовали (часто через `derive`).

---

## 9. Правило сироты (orphan rule) — частый затык

Ты можешь реализовать трейт для типа, **только если** трейт ИЛИ тип объявлены в твоём крейте. Нельзя
реализовать чужой трейт для чужого типа (например, `Display` для `Vec<T>` — оба не твои). Это защита от
конфликтов. Обход — обернуть чужой тип в свою структуру (паттерн newtype): `struct MyVec(Vec<T>)`.

---

## 10. Лучшие практики

- Заводи трейт, когда у **разных** типов есть **общее умение**, и ты хочешь писать код против умения, а не против типа.
- Для обобщённых функций предпочитай `impl Trait` / дженерик с bound (статика, быстро). `Box<dyn Trait>` — когда нужно хранить разные типы вместе или возвращать «какой-то» тип.
- Реализуй `From`, а не `Into` — `.into()` получишь бесплатно.
- Отдавай наружу DTO через `From`, пряча секреты модели. DTO — граница доверия.
- Не плоди трейты ради трейтов. Один тип, одна реализация — трейт не нужен, хватит обычного метода.
- Бесплатные трейты бери через `derive` (`Debug`, `Clone`, `Serialize`...) вместо ручных реализаций.

---

## 11. Шпаргалка ошибок

| Ошибка | Значение | Лечение |
|--------|----------|---------|
| `the trait ... is not implemented for ...` | у типа нет нужного умения | добавить `impl Trait for Тип` или `#[derive(...)]` |
| `cannot find method ... in current scope` | трейт с методом не подключён | `use путь::к::Трейту;` |
| `only traits defined in the current crate can be implemented for types defined outside` | нарушено правило сироты | обернуть в свой newtype-тип |
| `the trait ... cannot be made into an object` | трейт не object-safe для `dyn` | убрать дженерик-методы из трейта |
