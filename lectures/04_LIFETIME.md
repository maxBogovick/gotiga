# Лекция 4. Lifetime — время жизни ссылок

> Move (л.2) и borrow checker (л.3) уже познакомили тебя со ссылками. Lifetime — это последний кусок
> пазла: правило «ссылка не может жить дольше, чем то, на что она показывает». Эта лекция объясняет,
> что такое время жизни, зачем нужны аннотации `'a`, когда их можно не писать, и как читать ошибки про
> «does not live long enough».

---

## 1. Проблема, которую решают lifetimes

Опасная ситуация из языков без проверок (C, C++): функция возвращает указатель на локальную
переменную, которая тут же уничтожается. Получаешь «висячий указатель» (dangling pointer) — адрес есть,
а данных по нему уже нет.

```rust
// псевдо-C: так делать нельзя
fn broken() -> &str {
    let s = String::from("дом");
    &s            // вернуть ссылку на s...
}                 // ...но s уничтожается ЗДЕСЬ → ссылка повисла
```

Rust **не компилирует** этот код. Lifetime — это механизм, которым компилятор доказывает, что каждая
ссылка живёт **не дольше** своего источника. Если доказать нельзя — ошибка сборки, а не падение в проде.

---

## 2. Что такое lifetime буквально

Время жизни (lifetime) — это участок кода, на котором ссылка действительна. Компилятор для каждой
ссылки знает её lifetime и lifetime данных, и проверяет: `lifetime(ссылки) ⊆ lifetime(данных)`.

```rust
let r;                       // ─┐ область, где хотим жить r
{
    let x = 5;               //  │ ─┐ область жизни x
    r = &x;                  //  │  │
}                            //  │ ─┘ x умер здесь
println!("{}", r);           // ─┘ ❌ r ссылается на мёртвый x
```
Ошибка: `x does not live long enough` — «`x` не живёт достаточно долго, чтобы ссылка `r` была валидна за пределами блока».

---

## 3. Возврат ссылки из функции

Часто хочется вернуть **срез** входных данных без копирования — это эффективно. Пример из реального
`analytics.rs` (парсеры), упрощённо:

```rust
fn first_word(s: &str) -> &str {     // вернуть первое слово как срез s
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}
```
Это компилируется. Почему компилятор спокоен? Он применяет **правило элизии** (см. §5): раз есть один
входной `&str`, то возвращаемый `&str` живёт ровно столько же. То есть результат привязан к входу — и
пока жив вход, жив и результат. Никакого висячего указателя.

А вот это — не скомпилируется:
```rust
fn broken() -> &str {
    let s = String::from("дом");
    &s              // ❌ возвращаем ссылку на локальную s, которая сейчас умрёт
}
```
Ошибка `cannot return reference to local variable s`. Компилятор спас тебя от висячей ссылки.
**Решение:** верни владение — `String`, а не `&str`:
```rust
fn make() -> String {
    String::from("дом")   // ✅ отдаём владение наружу
}
```

---

## 4. Явные аннотации `'a` — когда компилятор просит помощь

Иногда из нескольких ссылок компилятор не может сам понять, к какой привязан результат. Тогда ты
подписываешь время жизни сам — именем `'a` (читается «лайфтайм а»; это просто метка, имя любое).

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```
Читается так: «существует некое время жизни `'a`; оба входа живут **хотя бы** `'a`; результат живёт
тоже `'a`». Этим ты обещаешь компилятору: возвращённая ссылка не переживёт **ни один** из входов.

Зачем это нужно? Потому что функция может вернуть и `a`, и `b` — компилятор не знает заранее какой.
Аннотация `'a` гарантирует: что бы ни вернулось, оно живо не дольше короче-живущего из аргументов.

```rust
let s1 = String::from("длинная строка");
let result;
{
    let s2 = String::from("кратко");
    result = longer(&s1, &s2);   // result привязан к min(жизнь s1, жизнь s2)
    println!("{}", result);      // ✅ тут оба живы
}
// println!("{}", result);       // ❌ s2 умер → result мог указывать на него
```

> Важно: аннотация `'a` **ничего не меняет** в работе программы и не продлевает жизнь. Она лишь
> **описывает** уже существующие отношения, чтобы компилятор мог их проверить.

---

## 5. Правила элизии — почему чаще аннотации НЕ нужны

В большинстве функций lifetime писать не надо: компилятор подставляет их сам по трём правилам элизии.
Тебе достаточно знать главный случай:

> Если у функции **один** входной параметр-ссылка, то все выходные ссылки получают его lifetime.

Поэтому `fn first_word(s: &str) -> &str` работает без аннотаций — выход привязан к единственному входу.
Аннотации нужны, когда входных ссылок **несколько** и неясно, к какой привязан результат (как в `longer`).

---

## 6. Структуры, которые держат ссылки

Если структура хранит ссылку, ты обязан указать lifetime — иначе непонятно, как долго структуре можно жить.

```rust
struct Label<'a> {
    text: &'a str,    // структура заимствует строку, не владеет ею
}

fn main() {
    let owner = String::from("экспонат");
    let label = Label { text: &owner };  // label заимствует owner
    println!("{}", label.text);          // ✅ owner жив
}                                        // label и owner умирают вместе
```
Правило: **`Label<'a>` не может пережить `owner`**, у которого одолжил строку. Если попробуешь —

```rust
let label;
{
    let owner = String::from("экспонат");
    label = Label { text: &owner };   // одолжили у owner
}                                     // owner умер
println!("{}", label.text);           // ❌ does not live long enough
```
— компилятор не пустит.

> Практический вывод: структуры со ссылками удобны для коротких «вьюшек» на чужие данные (парсеры,
> срезы конфигов). Если структура должна жить долго и независимо — пусть **владеет** данными (`String`,
> а не `&str`). В Gotiga почти все модели (`Order`, `Figurine`) владеют своими полями именно поэтому.

---

## 7. `'static` — «живёт всю программу»

Особый lifetime `'static` означает «данные живут до конца программы». Строковые литералы — `'static`,
потому что зашиты в бинарник:
```rust
let s: &'static str = "я живу вечно"; // литерал в бинарнике
```
Не пытайся лепить `'static` везде «чтобы скомпилировалось» — это почти всегда неверный способ обойти
ошибку. Обычно правильный ответ — вернуть владение (`String`), а не ссылку.

---

## 8. Lifetime в реальном коде Gotiga

В `analytics.rs` функции вроде `referrer_host`/`client_ip` сейчас возвращают `Option<String>` —
то есть **копируют** кусок строки. Это нормально и просто. Но если переписать их на возврат
`Option<&'a str>` (срез входа), копирование исчезнет — ценой того, что результат будет привязан к
времени жизни входной строки. Это упражнение из задачи 4.1: почувствовать разницу «вернуть копию
(`String`, владение)» против «вернуть вьюшку (`&str`, заимствование с lifetime)».

Также lifetime неявно живёт в каждом `&self`-методе сервиса: возвращая что-то, привязанное к `&self`,
ты не можешь пережить сам сервис. Обычно методы возвращают **владеемые** значения (`Order`, `Vec<...>`),
поэтому ты этого не замечаешь — и это сознательный выбор: меньше lifetime-боли.

---

## 9. Лучшие практики

- Сомневаешься — **верни владение** (`String`, `Vec<T>`), а не ссылку. Это проще и почти всегда достаточно быстро.
- Возвращай `&str`/`&[T]` только когда: данные уже где-то живут, копировать дорого, и время жизни очевидно (срез входа).
- Не пиши аннотации «на всякий случай» — пиши, только когда компилятор просит. Чаще их подставит элизия.
- `'static` — не «волшебное слово, чтобы собралось». Если тянет написать `'static` ради компиляции — почти наверняка нужно владение.
- В структурах предпочитай владение (`String`) ссылкам (`&str`), если это не короткоживущая вьюшка.

---

## 10. Шпаргалка ошибок

| Ошибка | Значение | Лечение |
|--------|----------|---------|
| `does not live long enough` | ссылка переживает источник | сузить жизнь ссылки, или вернуть владение |
| `cannot return reference to local variable` | возвращаешь ссылку на локалку | возвращай `String`/`Vec`, не `&...` |
| `missing lifetime specifier` | в структуре/функции нужна метка `'a` | добавить `<'a>` и привязать ссылки |
| `borrowed value does not live long enough` | то же, в контексте выражения | переставить порядок объявлений |
