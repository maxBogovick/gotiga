# battle-core — руководство разработчика

Правила боя «Скромных эпических битв». Здесь написано, **как с этим кодом работать**:
где что лежит, как добавить механику, что нельзя нарушать и чем проверять.

Про замысел — в документах наверху: [`BATTLE-REFERENCE.md`](../../BATTLE-REFERENCE.md)
(полный перечень механик), [`BATTLE-ARCHITECTURE.md`](../../BATTLE-ARCHITECTURE.md)
(почему счёт на сервере и как нарезаны этапы),
[`BATTLE-ENTITIES.md`](../../BATTLE-ENTITIES.md) (кто за что отвечает),
[`TASKS-BATTLE-ENGINE.md`](../../TASKS-BATTLE-ENGINE.md) (баланс и измерения).

## С чего начать

```bash
cd src-tauri/battle-core

cargo test                              # все правила и инварианты
cargo run --example partiya             # одна партия, читаемым текстом
cargo run --release --example svodka    # 2000 партий, числа про баланс
cargo doc --open                        # справка по типам
```

Партия целиком — цикл вокруг `reduce`; отдельный удар — `resolve` плюс `apply`.
Оба примера кода есть в справке крейта и **проверяются компилятором** (`cargo test --doc`),
так что они не могут разойтись с кодом.

## Что здесь есть и чего здесь нет

Крейт содержит правила и **больше ничего**. В `Cargo.toml` пустой список зависимостей,
и это не случайность — это способ сделать правило «ядро не знает про базу, сеть, часы и
случайность» механическим, а не устным.

| Нет здесь | Где будет |
|---|---|
| базы, HTTP, сессий | `gotiga-server`, слой службы |
| журнала на диске, `serde` | там же, когда матч начнут сохранять |
| текстов для человека | на фронте, в `en.ts`/`ru.ts` |
| случайности | нигде: её нет в игре |

Если в `src/` появился `use sqlx`, `SystemTime`, `rand` или `HashMap` — что-то пошло не
так. `HashMap` в этом списке потому, что порядок обхода у него не определён, а весь
крейт держится на воспроизводимости.

## Карта модулей

| Файл | За что отвечает |
|---|---|
| `board.rs` | клетки, расстояние по-королевски, ход в ширину по свободным клеткам |
| `card.rs` | `CardSnapshot` — карта, замороженная на момент партии |
| `unit.rs` | `Unit` — тело на поле; `Health`, `Status` и правила их наложения |
| `damage.rs` | пакет урона, конвейер, `resolve` (считает) и `apply` (меняет) |
| `event.rs` | `Event` — что случилось; `Outcome` — чем кончилось |
| `state.rs` | `MatchState`, `Action`, `reduce`, `legal_actions` — весь каркас |
| `bot.rs` | выбор действия за хранителя. Не правила, а игрок |

Зависимости строго вниз: `state` знает про `damage`, `damage` не знает про `state`.

## Пять понятий, без которых код не читается

| | |
|---|---|
| **`CardSnapshot` ≠ `Unit`** | Карта — неизменный шаблон. Тело — экземпляр на поле, со своим здоровьем и состояниями. Двух тел одной карты в партии — обычное дело |
| **`Action` ≠ `Event`** | Действие — что попросили (может быть отклонено). Событие — что случилось. Клиент проигрывает события |
| **`resolve` ≠ `apply`** | `resolve` считает и **не меняет никого** — поэтому её можно звать тысячу раз, спрашивая «а что если». `apply` — единственное, что пишет в тело |
| **`reduce` — единственная точка изменения** | Всё, что меняется в партии, меняется здесь. Больше нигде |
| **`legal_actions` — контракт с клиентом** | Всё, что там предложено, обязано быть принято. На этом стоит правило «клиент не знает правил» |

## Рецепты

### 1. Добавить шаг в расчёт урона

Например: «щит богов срезает четверть» или «раненые бьют слабее».

1. `damage.rs` → добавить вариант в `StepId`.
2. Написать функцию `fn step_xxx(amount: i32, ctx: &Ctx) -> i32`.
3. Вставить пару в `PIPELINE` **в нужное место** — позиция и есть порядок применения.
4. Перевод названия — не здесь. На фронте, по `StepId`.
5. Тест в `tests/rules.rs`: одно правило — один тест.

Ограничение осознанное: шаг видит бьющего и цель, но **изменить не может ничего**.
Подпись не позволяет. Если новому шагу нужно что-то расходовать (как щит) — он пока
пишется ниже цикла, рядом со щитом, и это шов, о котором надо знать.

### 2. Добавить новый глагол (щит, урон со временем, яд)

**Сначала — ограничение, которое сейчас есть.** Большинство глаголов словаря ещё
не в крейте: `Action::Attack` жёстко берёт базовый удар тела. **Лечение — первое
исключение:** активная способность `heal` формы `one` или `self` уже читается из
`CardSnapshot.abilities` (своя дальность, мана, перезарядка), а поле тела `mend`
остаётся запасным путём для карт без способности. Остальные глаголы по-прежнему
заводятся свойством тела, наравне с `power`, пока не подъедут следом.

Порядок, по которому пойдёт каждый следующий глагол словаря:

1. **`event.rs`** — что увидит зритель: `Event::Healed { target, amount }`.
2. **`damage.rs` или новый `heal.rs`** — та же пара функций:
   `fn resolve_heal(target: &Unit, amount: i32) -> HealResolution` (считает, не меняет)
   и `fn apply_heal(target: &mut Unit, res: &HealResolution) -> Vec<Event>`.
   Лечение не поднимает выше исходного — это правило живёт в `resolve_heal`.
3. **`state.rs`** — новый вариант `Action`, ветка в `match` внутри `reduce`,
   новые причины отказа в `Illegal`.
4. **`state.rs` → `legal_actions`** — предложить действие клиенту. **Забыть этот шаг —
   самая частая ошибка**: механика работает, но её нет в интерфейсе, и тест
   `nothing_the_legal_list_offers_is_ever_refused` про это молчит, потому что проверяет
   обратное направление.
5. **`bot.rs`** — научить бота этим пользоваться, иначе прогонщик не увидит механику.
6. **Тесты**: правило в `tests/rules.rs`, взаимодействие с ходом — в `tests/frame.rs`.
7. **`examples/partiya.rs`** — показать событие, иначе оно невидимо глазом.
8. **`tests/invariants.rs` → `generate`** — научить генератор выдавать тела с новой
   механикой. Пропустить этот шаг легко, и тогда батарея из 500 партий будет зелёной,
   ни разу не задев новое. Ничто об этом не предупредит.
9. **Перечитать прежние инварианты — не ослабли ли они.** Самая коварная из заминок:
   проверка «нанесено не меньше, чем потеряно» продолжала проходить после появления
   лечения, но перестала что-либо значить, потому что лечение уменьшает потерянное.
   Пришлось дописать в неё слагаемое. Зелёный тест ≠ работающая проверка.

Признак, что глагол сделан правильно: **все прежние тесты прошли без правок.** Так было
с `move` и с `mend`, и так должно быть дальше.

### 3. Добавить свойство телу

`card.rs` (`CardSnapshot` + `with_…`), затем `unit.rs` (`Unit`, `Unit::new`,
`Unit::from_card`). Оба места обязательны — иначе свойство есть на карте и теряется
при постановке на поле.

### 4. Добавить состояние (благословение, проклятие)

Обычно кода не требуется: `Status::new(имя, Stat, величина, ходы)` и
`unit.apply_status(...)`. Новая **ось** — да, требует: вариант в `Stat`, чтение в том
шаге конвейера, который его касается.

Правила наложения уже реализованы и покрыты тестами: одноимённое обновляет срок,
разноимённое складывается, потолок пять, смерть снимает всё. Их не надо повторять в
каждом глаголе — надо звать `apply_status`.

### 5. Поменять поведение бота

`bot.rs`, функция `choose`. Порядок предпочтений — сверху вниз: добить, выставить тело,
ранить слабейшего, шагнуть навстречу, пас.

Два запрета, и они не про вкус:

- бот **не видит** того, чего не видит игрок;
- бот **не получает** поблажек в числах.

Сложность = глубина перебора. Победа над жульничающим ботом ничего не говорит о силе
карты, то есть ломает измерение баланса — половину того, ради чего этот крейт написан.
Перебор на 2–3 хода строится вызовом той же `reduce`; это возможно только потому, что
она чистая.

## Чем проверять

| Файл | Что проверяет |
|---|---|
| `tests/rules.rs` | одно правило — один тест: броня, каналы, минимум 1, щит, состояния, след |
| `tests/frame.rs` | поле, ход, экономика действий, шаг, конец партии, бот |
| `tests/invariants.rs` | 500 сгенерированных партий: завершаемость, целость поля, детерминизм, честность `legal_actions` |
| `examples/svodka.rs` | баланс: длина партий, перевес первого хода, дальность против ближнего боя |
| `tools/mutants.py` | **проверка самих проверок**: ломает математику по одному месту и смотрит, падает ли хоть один тест |

Генератор партий живёт **в тесте**, не в крейте: посев задан руками, поэтому падение
называет точный `seed` и воспроизводится повторным запуском.

### Проверка самих проверок

Зелёные тесты не значат, что математика проверена — значит только, что они не спорят
с кодом. `tools/mutants.py` ломает правила по одному месту и смотрит, замечает ли это
хоть кто-нибудь:

```bash
python3 tools/mutants.py
```

**Выжившая мутация — это либо дыра в проверках, либо доказательство, что правка ничего
не меняет** (перестановка двух сложений, например). Разобрать надо каждую. Первый прогон
нашёл две настоящие дыры: `strike` могла всегда брать телесный канал, и лечение
отрицательной величиной могло ранить, — обе не замечались ни одним из 79 тестов.

Добавили глагол — допишите в `MUTATIONS` пару строк про его математику.

**Перед тем как считать механику готовой:**


```bash
cargo test                              # все прежние тесты — без правок
cargo test --doc                        # примеры в справке ещё компилируются
cargo run --release --example svodka     # числа не уехали
```

## Чего нельзя делать (лист ревью)

1. **Не заводить зависимости** в `Cargo.toml` без разговора. Пустой список — это правило,
   а не случайность.
2. **Не менять ничего вне `reduce`.** Единственная точка изменения — весь фундамент.
3. **Не звать часы и случайность.** Ни `SystemTime`, ни `rand`, ни `HashMap`.
4. **Не писать человеческий текст в ядро.** Ядро даёт признаки (`StepId`, `Illegal`),
   слова подбирает тот, кто показывает. Дом двуязычный.
5. **Не добавлять глагол, не добавив его в `legal_actions`.**
6. **Не менять подпись `reduce`, формат журнала и форму `legal_actions`.** Если новая
   механика этого требует — она не механика, а изменение каркаса, и это отдельный
   разговор.
7. **Не чинить баланс в коде правил.** Числа правятся числами и проверяются прогонщиком.

## Что будет дальше

- **`serde`** — придёт в день, когда журнал начнут писать в базу. Это derive на тех же
  структурах, форма не меняется.
- **Workspace** — крейт станет членом `src-tauri/Cargo.toml`, сервер получит его в
  зависимости. Границу по-прежнему держит `Cargo.toml`, а не уговор.
- **WASM** — если однажды понадобится мгновенный отклик на клиенте, собирается **тот же
  крейт**, а не вторая реализация правил на TypeScript. Ради этого здесь и нет
  зависимостей.
